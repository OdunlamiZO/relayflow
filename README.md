# RelayFlow

RelayFlow is an omnichannel customer messaging platform with developer-grade workflow automation. Telegram is the first adapter, WhatsApp Business Cloud API support has started, and Instagram is planned. The core model is channel-agnostic.

Contributions are welcome — see [`CONTRIBUTING.md`](CONTRIBUTING.md), and [`ROADMAP.md`](ROADMAP.md) for planned work.

## Repository Layout


## Local Development

Prerequisites:

- Java 21
- Maven 3.9+
- Node.js 20+
- Docker

Start infrastructure:

```bash
# Core (postgres + redis)
docker compose up -d dev-postgres dev-redis

# Core + Ollama (self-hosted LLM, pulls llama3.2 on first run)
docker compose --profile dev --profile ollama up -d
```

Build the plugin API and the official plugins once, and again after changing them. `make plugins` installs the modules into your local Maven repository and copies the plugin JARs to `apps/api/plugins`, where the API loads them:

```bash
make plugins
```

Flyway is disabled at runtime, so migrations do not run automatically when the API starts. Run migrations manually before starting the API against a fresh or changed database:

```bash
cd apps/api
mvn flyway:migrate \
  -Dflyway.url=jdbc:postgresql://localhost:5432/relayflow \
  -Dflyway.user=relayflow \
  -Dflyway.password=relayflow
```

Set a credential encryption key (required — the API refuses to start without it):

```bash
export RELAYFLOW_ENCRYPTION_KEY=$(openssl rand -base64 32)
```

Run the API:

```bash
cd apps/api
mvn spring-boot:run
```

Logs are human-readable by default. For structured logs, set `LOG_FORMAT` to `json` (Datadog and most log agents), `ecs` (Elastic), `gelf` (Graylog), or `logfmt` (Loki):

```bash
LOG_FORMAT=json mvn spring-boot:run
```

Enable Google login locally:

```bash
export GOOGLE_AUTH_ENABLED=true
export GOOGLE_CLIENT_ID=your-google-client-id
export GOOGLE_CLIENT_SECRET=your-google-client-secret
export RELAYFLOW_WEB_BASE_URL=http://localhost:3000
```

Per-channel-account Telegram bots are registered with a generated `secret_token` and verified automatically via the `X-Telegram-Bot-Api-Secret-Token` header.

Configure this redirect URI in Google Cloud:

```text
http://localhost:3000/backend/login/oauth2/code/google
```

Run the web app:

```bash
cd apps/web
npm install
npm run dev
```

The browser only talks to the web app: requests to `/backend/*` are forwarded to the API at `RELAYFLOW_API_INTERNAL_URL` (default `http://localhost:8080`), so the session cookie belongs to the web app's domain.

The first account created on a fresh instance goes through instance bootstrap (`/setup` in the web app), not the normal signup form — see [Authentication](#authentication) below.

## API Reference

### Health

- `GET /health`

### Authentication

- `GET  /auth/me`
- `GET  /auth/bootstrap-status`
- `POST /auth/bootstrap`
- `POST /auth/signup`
- `POST /auth/login`
- `POST /auth/login/2fa`
- `POST /auth/reset-password/{token}` — set a new password from a link generated via `/profile/request-password-reset` or by a workspace owner
- `POST /auth/logout`
- `GET  /oauth2/authorization/google`
- `GET  /login/oauth2/code/google`

RelayFlow is single-tenant-per-instance: the first account on a fresh instance is created via `POST /auth/bootstrap` (gated by `userRepository.count() == 0`, checked with `GET /auth/bootstrap-status`), which creates the first admin account and their workspace in one step with no email verification round-trip. Every account after that requires a valid workspace invite token — `POST /auth/signup` takes `inviteToken` and reuses invite-acceptance validation, so there is no open public signup endpoint. The app supports email/password login, Google OAuth, and TOTP two-factor login.

There is no self-service "change password" form — a password only ever changes via a single-use reset link (`PasswordResetToken`, 1 hour expiry), requested from the profile page (`POST /profile/request-password-reset`) or generated by a workspace owner for a member (`POST /workspaces/{workspaceId}/members/{memberId}/reset-password`), and consumed via `POST /auth/reset-password/{token}`.

### Integrations

- `GET    /workspaces/{workspaceId}/api-keys`
- `POST   /workspaces/{workspaceId}/api-keys`
- `DELETE /workspaces/{workspaceId}/api-keys/{keyId}`
- `GET    /workspaces/{workspaceId}/secrets` — list a workspace's named secrets (names only, never values)
- `POST   /workspaces/{workspaceId}/secrets` — create a secret
- `PUT    /workspaces/{workspaceId}/secrets/{secretId}` — replace a secret's value; the old value can't be recovered
- `DELETE /workspaces/{workspaceId}/secrets/{secretId}`

All secret endpoints require `SECRETS_WRITE` permission or owner role. Reference a secret in a workflow's HTTP Request node (URL, headers, or body) as `{{secrets.NAME}}` — the decrypted value is resolved only at request time and never appears in the workflow definition, a run log, or an API response.

- `GET    /workspaces/{workspaceId}/hooks` — list the workspace's custom hooks
- `GET    /workspaces/{workspaceId}/hooks/built-in` — list the built-in hooks (email, phone number, number, whole number, date, web address)
- `POST   /workspaces/{workspaceId}/hooks` — create a custom hook; rejects an expression FEEL can't parse
- `PUT    /workspaces/{workspaceId}/hooks/{hookId}` — update a custom hook; applies immediately to every workflow and AI agent using it
- `DELETE /workspaces/{workspaceId}/hooks/{hookId}` — refused with 409 while a workflow or AI agent still uses the hook
- `POST   /workspaces/{workspaceId}/hooks/test` — evaluate an unsaved expression against a sample value

Listing hooks requires workspace membership; the other hook endpoints require `WORKFLOWS_WRITE` permission or owner role. Hooks are [FEEL](https://docs.camunda.io/docs/components/modeler/feel/what-is-feel/) expressions evaluated by Camunda's `feel-engine`, with Java calls from expressions disabled and a 2-second evaluation timeout. An open-ended Ask Question node can use one (`validationHook`) to validate and transform the contact's reply. A rejected voice reply is first converted by the workspace's chat model, then checked again. A reply that's still rejected is answered with the hook's error message and asked again, up to the node's attempt limit, after which the run follows the node's `invalid` branch.

- `GET    /workspaces/{workspaceId}/webhooks` — list every webhook configured for the workspace
- `POST   /workspaces/{workspaceId}/webhooks` — create a new webhook
- `PUT    /workspaces/{workspaceId}/webhooks/{webhookId}` — update a webhook's URL, enabled state, or subscribed event types
- `DELETE /workspaces/{workspaceId}/webhooks/{webhookId}`
- `POST   /workspaces/{workspaceId}/webhooks/{webhookId}/rotate-secret` — generates a new HMAC secret and returns it once; it can't be retrieved again after this response

All webhook endpoints require `WEBHOOKS_WRITE` permission or owner role. A workspace can have any number of webhooks, each with its own URL and event subscriptions.

Public API requests authenticate with `X-Api-Key`:

- `GET  /public/v1/conversations`
- `GET  /public/v1/conversations/{id}`
- `GET  /public/v1/conversations/{id}/messages`
- `POST /public/v1/conversations/{id}/messages` — sends an outbound message; a closed conversation stays closed
- `PUT  /public/v1/contacts/{id}/tags` — sets contact tags, e.g. `{"kyc_status": "verified"}`; `null` clears a tag; an undefined tag returns `UNKNOWN_TAG` and a value outside its allowed list returns `INVALID_TAG_VALUE`

Every public API error is [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem details (`application/problem+json`). Branch on `code`; `detail` says what went wrong:

```json
{
  "type": "/problems/conversation-not-found",
  "title": "Conversation not found",
  "status": 404,
  "detail": "Conversation not found",
  "instance": "/public/v1/conversations/6f1c…",
  "code": "CONVERSATION_NOT_FOUND"
}
```

| `code` | Status | When |
| --- | --- | --- |
| `INVALID_REQUEST` | 400 | A field fails validation, the body isn't valid JSON, or a parameter has the wrong type |
| `UNKNOWN_TAG` / `INVALID_TAG_VALUE` | 400 | The tag isn't defined, or the value isn't in its allowed list |
| `MISSING_API_KEY` / `INVALID_API_KEY` | 401 | No `X-Api-Key` header, or the key is unknown, revoked, or expired |
| `CONVERSATION_NOT_FOUND` / `CONTACT_NOT_FOUND` | 404 | No such conversation or contact in the key's workspace |
| `RESOURCE_NOT_FOUND` | 404 | Any other record the request needs is missing |
| `ENDPOINT_NOT_FOUND` | 404 | No endpoint at that path |
| `METHOD_NOT_ALLOWED` | 405 | The endpoint doesn't support that HTTP method; see the `Allow` header |
| `CONVERSATION_LOCKED` | 409 | A workflow is handling the conversation |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | The body isn't `application/json` |
| `RATE_LIMITED` | 429 | Too many requests; retry after the `Retry-After` header's seconds |
| `INTERNAL_ERROR` | 500 | Something failed on the server |
| `CHANNEL_DELIVERY_FAILED` | 502 | Telegram or WhatsApp didn't accept the message |

The rest of the API keeps its `{"message", "timestamp"}` error body.

## AI Agent Configuration

The AI agent is off by default. Enable it per workspace in **Settings → AI Agent**.

### LLM provider

LLM providers are [plugins](docs/plugins.md). The API image ships two official ones: **Anthropic** (`ANTHROPIC`) and **OpenAI-compatible** (`OPENAI_COMPATIBLE`) — any API that speaks OpenAI's chat completions format (OpenAI, Groq, OpenRouter, Together, DeepSeek, Mistral, Ollama, vLLM, LM Studio, …). Install another plugin to use a different provider; its ID goes in the Redis keys below.

Each workspace chooses its provider and model in **Settings → Providers** (owners only). An agent left on "Workspace default" (the default for a new agent) follows that choice; an agent can also be pinned to a specific provider from its settings.

A workspace that hasn't chosen a provider uses the instance default, a Redis key. Switch it at any time without restarting:

```bash
redis-cli SET platform:llm:provider 'OPENAI_COMPATIBLE'
redis-cli SET platform:llm:provider 'ANTHROPIC'
```

Nothing is chosen for you. With no provider from the agent, the workspace, or this key, the AI agent doesn't reply and hands conversations to a person. Every provider also needs a model, from **Settings → Providers** or the model keys below (a workspace's own model wins). A plugin whose environment variables are missing shows as "not configured" there, and the API logs `Plugin provider isn't configured` at startup.

The former values `OPENAI`, `GROQ`, `OLLAMA` and `OPENROUTER` are still accepted and mean `OPENAI_COMPATIBLE`.

### Anthropic

```bash
export ANTHROPIC_API_KEY=sk-ant-...
redis-cli SET 'platform:llm:anthropic:model' 'claude-haiku-4-5'
```

### OpenAI-compatible

Set the API's base URL (including `/v1`) and key as env vars, then choose the model in Redis — there's no default, so the provider fails until it's set:

```bash
export OPENAI_COMPATIBLE_BASE_URL=https://api.groq.com/openai/v1
export OPENAI_COMPATIBLE_API_KEY=gsk_...
redis-cli SET 'platform:llm:openai-compatible:model' 'llama-3.3-70b-versatile'
redis-cli SET platform:llm:provider 'OPENAI_COMPATIBLE'
```

| Provider | `OPENAI_COMPATIBLE_BASE_URL` | Example model | Notes |
|---|---|---|---|
| Groq | `https://api.groq.com/openai/v1` | `llama-3.3-70b-versatile` | Free tier with daily limits, very fast. Keys at [console.groq.com](https://console.groq.com) |
| OpenRouter | `https://openrouter.ai/api/v1` | `openai/gpt-4o-mini` | One key for hundreds of models — see [openrouter.ai/models](https://openrouter.ai/models). `:free` models are heavily rate-limited |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` | |
| Ollama | `http://localhost:11434/v1` | `llama3.2` | Self-hosted, no key — leave `OPENAI_COMPATIBLE_API_KEY` empty |

The model must support JSON output (`response_format: json_object`). On OpenRouter, RelayFlow asks to be routed only to hosts that support it, so a model with no such host fails (and the conversation is escalated) instead of replying in a format the agent can't read. Pick a general-purpose chat model — speech, embedding, and safety-classifier models won't work.

Changing the URL or key needs a restart; changing the model in Redis takes effect on the next message.

### Ollama (self-hosted, free)

Ollama is included in `docker-compose.yml` as an opt-in profile:

```bash
# Starts postgres + redis + ollama; pulls llama3.2 automatically (~2 GB on first run)
docker compose --profile dev --profile ollama up -d
```

Or install it directly (`brew install ollama`, then `ollama serve` and `ollama pull llama3.2`). Either way, point the OpenAI-compatible provider at it:

```bash
export OPENAI_COMPATIBLE_BASE_URL=http://localhost:11434/v1
redis-cli SET 'platform:llm:openai-compatible:model' 'llama3.2'
redis-cli SET platform:llm:provider 'OPENAI_COMPATIBLE'
```

The default `llama3.2` pull is a small (~3B) model; larger local models or a hosted provider follow the agent's instructions more reliably.

### Voice messages

Voice notes and audio files from Telegram and WhatsApp are downloaded, stored, and transcribed by plugins. The API image ships a transcription plugin for any OpenAI-format speech-to-text API (`OPENAI_COMPATIBLE`) and a storage plugin that writes to a folder (`LOCAL_DISK`). A transcribed voice note reaches workflows and the AI agent like a text message, and the inbox plays the recording next to its transcript. Without a transcript, the voice note waits in the inbox for a person to reply.

Point the transcription plugin at a speech-to-text API. It uses the OpenAI-compatible LLM settings when these are unset:

```bash
export OPENAI_COMPATIBLE_TRANSCRIPTION_BASE_URL=https://api.groq.com/openai/v1
export OPENAI_COMPATIBLE_TRANSCRIPTION_API_KEY=gsk_...
redis-cli SET 'platform:transcription:openai-compatible:model' 'whisper-large-v3-turbo'
```

Recordings are saved under `RELAYFLOW_STORAGE_DIRECTORY` (the API image uses `/app/data/storage`, a Docker volume). Nothing is transcribed or stored until a provider is chosen, in **Settings → Providers** or for every workspace in Redis:

```bash
redis-cli SET platform:transcription:provider 'OPENAI_COMPATIBLE'
redis-cli SET platform:storage:provider 'LOCAL_DISK'
```

Recordings over 25 MB are not downloaded.

## Git Hooks

The repository includes `hooks/pre-commit`. It runs:

- Backend Java formatting check: `mvn spotless:check -Pdevelopment`
- Backend unit tests: `mvn test`
- Frontend lint: `npm run lint`
- Frontend typecheck: `npm run typecheck`
- Frontend format check: `npm run format:check`
- Frontend unit/component tests: `npm run test`
- Marketing lint, typecheck, format check, and unit tests (`apps/marketing`)

Install with:

```bash
mvn install -Pdevelopment
```

## Tests

### Frontend

```bash
cd apps/web
npm run test          # unit / component tests (pre-commit)
npm run test:watch    # watch mode
```

Playwright end-to-end tests should be added later for the inbox and workflow builder flows. Keep them out of pre-commit; run in CI or a pre-push hook.

### Backend

Run from the repository root; this builds the plugin API and the official plugins too.

```bash
mvn install -Pdevelopment          # lightweight tests, no Docker needed
mvn verify -Pintegration-test      # full integration tests against PostgreSQL (requires Docker)
```
