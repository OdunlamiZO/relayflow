# RelayFlow

Product Requirements and Technical Strategy | Updated October 2, 2026

## 1. Product Summary

RelayFlow is an omnichannel customer messaging platform with developer-grade workflow automation and an optional AI agent, built on a channel-agnostic core rather than around any single platform — see Section 4 for which adapters are live and Section 5.3 for what's next. The core model is designed around users, identities, preferences, MFA methods, workspaces, workspace members and permissions, channel accounts, contacts, external identities, conversations, messages, integrations, and workflow definitions.

RelayFlow is free and open source, distributed as self-hosted (BYOC) software: operators run their own Docker Compose stack on their own infrastructure. The product differentiates on reliable automation — mutable workflow variables, controllable HTTP behavior, visible execution logs, durable message handling — plus an AI agent that can draft or auto-send replies within operator-defined guardrails.

## 2. Problem

- Messaging workflow tools often make variables hard to override, inspect, and reuse.
- HTTP/API steps frequently hide important controls such as timeout, response mapping, retry, and error branching.
- Failed automations are difficult to debug when step inputs, outputs, branch decisions, and variables are not visible.
- Small businesses need a simple inbox, while technical operators need predictable workflow execution.
- Teams that need to own their data and avoid recurring SaaS billing need a credible self-hosted option, not just a hosted multi-tenant product.

## 3. Target Market

The target market is SMB and technical teams handling support, sales, and operations across messaging channels who want to self-host rather than depend on a vendor's hosted multi-tenant instance. These teams rarely stay on one channel by choice — their customers are scattered across whichever platform is locally dominant, so a tool that only speaks one channel forces them to either bolt on separate point solutions per platform or leave some customers unserved. RelayFlow's channel-agnostic core (Section 1) is what makes it viable for this segment specifically.

## 5. Product Scope

### 5.1 MVP Goal

Prove that RelayFlow can normalize Telegram and WhatsApp conversations into a channel-agnostic inbox, run configurable workflows with transparent execution data, and ship as self-hosted software an operator can run on their own infrastructure.

### 5.2 Implemented MVP Features

- Workspace and user account system.
- Instance bootstrap for the first account and workspace on a fresh deployment (no email verification round-trip — the operator already has server access); every account after that requires a valid workspace invite token.
- Google login and TOTP two-factor login.
- Password reset via a single-use, 1-hour link — self-requested from the profile page, or generated by a workspace owner for a member; there is no self-service in-place password change.
- Telegram bot connection as the pilot channel adapter.
- WhatsApp Business Cloud API connection with webhook verification, inbound text and interactive button-reply ingestion, outbound text/button relay, and settings UI.
- Generic contact, external identity, conversation, and message models, including contact list/detail/delete/merge flows.
- Contact custom fields (six reserved fields plus a per-workspace schema) and contact tags with a fixed list of values and optional colours.
- Contact access: everyone, or only whitelisted phone numbers. In whitelist mode other senders are ignored and nothing is stored; WhatsApp senders are checked by number, and Telegram users share their number once with Telegram's share button.
- Agent inbox with conversation list, message thread, outbound reply composer, conversation assignment, conversation status updates, escalation indicator, and workflow lock handling.
- Real-time updates through workspace SSE events.
- Workflow definition CRUD and React Flow-based builder.
- Workflow trigger for conversation_opened events.
- Workflow nodes: Trigger, Send Message, Condition, HTTP Request, Set Variable, Set Contact Field, Set Contact Tag, Ask Question, Jump To, End Conversation. Ask Question supports open-ended replies (optionally checked by a hook) and defined options with option-number matching, selection variables, Telegram reply keyboards, WhatsApp buttons for up to three options, and a "No reply" output after a timeout.
- Hooks: built-in (email, phone number, number, whole number, date, web address) or custom FEEL expressions that check and clean up Ask Question replies and AI-extracted values.
- Workspace secrets, encrypted at rest and referenced in HTTP Request nodes as `{{secrets.NAME}}`.
- Persisted workflow runs and per-step input/output snapshots, exposed through a run logs UI.
- Workflow publish validation for structural graph rules, including valid Jump To targets.
- Workspace member permissions for inbox, contacts, contact fields, workflows, channels, AI agents, API keys, webhooks, and secrets, with guarded owner transfer.
- Workspace invites with expiring tokens and permission assignment — also the gate for all non-bootstrap account creation.
- Workspace API keys and public API endpoints for conversations, messages, outbound replies, and contact tags. Messages sent through the public API don't reopen a closed conversation.
- Multiple workspace webhooks, each with its own encrypted HMAC secret, signature header, retry/backoff delivery, and subscribed events: `contact.created`, `contact.updated`, `contact.deleted`, and `contact.merged`.
- AI agents: multiple per workspace, with a default and per-channel assignment. Each has its own configuration (autonomy ceiling, instructions, knowledge base Q&A, escalation keywords, extraction fields with optional hooks, workflow mappings to published workflows) and LLM provider (Anthropic, OpenAI, Groq, self-hosted Ollama), switchable without restart. A decision pipeline (keyword escalation → LLM → escalate/draft/auto-send) and an inbox draft banner, where drafts can be edited before sending, cover AI-suggested replies and workflow triggers. An escalation stamps the conversation and clears on the next human reply; failed-call and error escalations also clear on the agent's next successful LLM call.
- Self-hosted distribution: Docker Compose production stack (api, web, Postgres, Redis, Caddy for automatic TLS, a one-shot Flyway migrate service).

### 5.3 Not Yet Implemented

- Manual workflow test-run mode.
- Published workflow version history separate from draft graph.
- Broader role model beyond current owner/member permissions.
- Retry count, retry delay, and backoff controls for HTTP nodes.
- Secret masking in workflow editor previews and run logs.
- WhatsApp webhook signature verification (beyond the initial verify-token handshake).
- Additional channel adapters beyond Telegram and WhatsApp (Instagram planned).
- Restricting `POST /workspaces` (creating additional workspaces) — currently any authenticated user can create one; only account creation and the first workspace are gated today.
- Proactive session revocation on password reset — a reset rotates the credential but does not invalidate other active sessions for that user (no session registry exists today; would need either a lazy per-request staleness check or a shared session store).

### 5.4 Out Of Scope For Current MVP

- Broadcast campaigns.
- Advanced analytics.
- Native mobile apps and push notifications — would need a centralized relay RelayFlow operates, which doesn't fit self-hosted distribution.
- A hosted multi-tenant SaaS instance of the core product — apps/api and apps/web are self-hosted-only.
- Monetization — the product is free and open source; no billing model exists.
- Marketplace integrations.
- Full CRM functionality.

## 6. User Stories

- As an operator, I can bootstrap a fresh self-hosted instance into a working admin account and workspace in one step.
- As a workspace owner, I can invite a teammate by email; they must accept the invite to gain access — there is no open public signup.
- As a workspace owner, I can create or switch workspaces.
- As a workspace owner, I can connect a Telegram bot or WhatsApp Business Cloud API account so messages enter RelayFlow.
- As an agent, I can view conversations and reply from the inbox when I have inbox permission and no active workflow owns the conversation.
- As an agent, I can assign a conversation to a teammate, or unassign it.
- As a user, I can update my profile, request a password reset link, and enable/disable TOTP 2FA.
- As a workspace owner, I can generate a password reset link for a member on their behalf.
- As an admin, I can create a workflow triggered when a conversation opens.
- As an admin, I can create and overwrite workflow variables.
- As an admin, I can call an external API with configurable method, URL, headers, body, content type, timeout, and response mappings.
- As an admin, I can publish only workflows that pass graph validation.
- As an admin, I can inspect every workflow run and step in the run logs UI.
- As a workspace owner, I can invite members, transfer ownership to another member, and grant only the permissions each person needs.
- As an integrator, I can use API keys to read conversations/messages, send outbound replies, and set contact tags.
- As an integrator, I can subscribe to signed workspace webhook events when contacts are created, updated, deleted, or merged.
- As a workspace owner, I can limit who can message the workspace to whitelisted phone numbers.
- As an admin, I can define contact fields and tags, and set them from workflows, the contact page, or the public API.
- As an admin, I can validate and clean up contact replies and AI-extracted values with hooks.
- As a workspace owner, I can enable an AI agent that drafts or auto-sends replies within instructions and autonomy limits I control, and escalates to a human on defined keywords or low confidence.
- As an agent, I can see at a glance which conversations the AI agent has escalated, until I reply and clear it.
- As an operator, I can download and self-host RelayFlow for free.

## 7. Workflow Requirements

### 7.1 Implemented Nodes

- Trigger: starts from conversation_opened.
- Send Message: sends an outbound workflow message through the channel adapter.
- Condition: supports multiple branches and comparison operators.
- HTTP Request: supports method, URL, headers, body, content type, timeout, success/error branches, status variable, and JSON response mappings.
- Set Variable: creates or overwrites a variable.
- Set Contact Field: writes a contact custom field.
- Set Contact Tag: sets or clears a contact tag.
- Ask Question: sends a question, pauses the run, resumes when the contact replies, supports exact option or numeric option matching, and can save the selected value into a variable. An open-ended reply can be checked by a hook ("Invalid" output); if the contact doesn't reply before the timeout, the step fails and the run follows "No reply".
- Jump To: redirects execution to another node by ID with a configurable max-jump limit to prevent unbounded loops.
- End Conversation: optionally sends a closing message and sets the conversation to closed.

### 7.2 Variable System

The current runtime uses a flat variable map with dot-notation names. Built-in variables include workspace, conversation, contact (including `contact.tags.<key>`), channel, triggering message, and `secrets.<name>` values. User-defined variables are produced by Set Variable, HTTP response mappings, and Ask Question responses.

- Variables are mutable and can be overwritten.
- Text interpolation uses `{{variable}}` placeholders.
- HTTP response mappings can write JSON path values into workflow variables.
- Step input snapshots and output snapshots are persisted for observability.
- Formal system/contact/conversation/workflow/node-output scopes remain a design target; current implementation approximates this with dot-notation keys.
- Workspace secrets are resolved only when an HTTP request is sent; masking them in previews and run logs is still planned.

### 7.3 HTTP Step

- Implemented: GET, POST, PUT, PATCH, DELETE.
- Implemented: URL interpolation, headers, body, content type, timeout in seconds, and `{{secrets.NAME}}` references.
- Implemented: 2xx routes to success; non-2xx/network errors route to error and set error.message.
- Implemented: response status variable and JSON path response mappings.
- Planned: retry count, retry delay/backoff, auth helpers, and secret masking.

## 8. Architecture

- Three independently deployable apps: apps/api (Java Spring Boot), apps/web (Next.js product frontend), and apps/marketing (a static Next.js marketing site).
- apps/api and apps/web are distributed self-hosted-only via Docker Compose; RelayFlow does not run a hosted multi-tenant instance of the core product. apps/marketing is a static site with no backend, hosted on GitHub Pages.
- PostgreSQL stores users, workspaces, members, invites, API keys, webhooks, secrets, hooks, channel accounts, contacts, external identities, whitelisted phone numbers, conversations, messages, workflow definitions, runs, run steps, and AI agent configuration/invocation/draft data.
- Flyway migrations are run manually; the API does not auto-migrate on startup (a dedicated one-shot Docker service runs them in production).
- Telegram and WhatsApp webhooks normalize provider payloads into channel-agnostic records, including WhatsApp interactive button replies, after the workspace's contact access check.
- The web app reaches the API through its own `/backend` path.
- SSE broadcasts workspace updates, including AI draft creation and escalation, to open inbox sessions.
- Workflow definitions are stored as React Flow-style draft graph JSON.
- Workflow execution is asynchronous, locks conversations while active, and records durable run/step logs.

## 9. Technology Stack

- Backend (apps/api): Java 21, Spring Boot, Spring Security, Spring Data JPA, Flyway, PostgreSQL, Redis.
- Frontend (apps/web): Next.js, React, TypeScript, Tailwind CSS, TanStack Query, React Flow.
- Marketing (apps/marketing): Next.js static export, deployed to GitHub Pages.
- AI agent: pluggable LLM layer over Anthropic, OpenAI, Groq, and self-hosted Ollama.
- Contracts: OpenAPI 3.1 and JSON Schema.
- Testing: Maven/JUnit on the backend; Vitest and Testing Library on both frontends.
- Deployment: Docker Compose for local infrastructure (PostgreSQL, Redis, optional Ollama) and for the self-hosted production stack (adds Caddy for automatic TLS and a one-shot migration service).

## 10. Data Model

- `users`: core account/profile lifecycle fields.
- `user_identities`: email and Google authentication identities.
- `user_preferences`: reserved for future per-user preferences — currently holds no fields beyond identity/timestamps. Its one prior field, an email-updates opt-in, was removed once RelayFlow became self-hosted-only (no marketing emails to opt into).
- `password_reset_tokens`: single-use, 1-hour-expiry tokens for setting a new password — the only path a password is ever set after signup.
- `user_mfa_methods` and `two_factor_challenges`: TOTP setup/login state.
- `workspaces`, `workspace_members`, and `workspace_member_permissions`: tenant, membership, and permission boundary. Workspaces also hold the contact field and tag definitions and the contact access setting with its default country.
- `workspace_invites`: expiring invite tokens with permission sets — the gate for every account created after instance bootstrap.
- `workspace_api_keys`: hashed public API keys with revocation, expiry, and last-used tracking.
- `workspace_webhooks` and `workspace_webhook_events`: outbound webhook configuration and subscribed events (`contact.created`, `contact.updated`, `contact.deleted`, `contact.merged`).
- `workspace_secrets`: encrypted values referenced by HTTP Request nodes.
- `hooks`: custom FEEL hooks.
- `whitelisted_phone_numbers`: E.164 numbers allowed to message a whitelist-only workspace.
- `channel_accounts`: provider connection records and encrypted credentials.
- `contacts` and `external_identities`: channel-neutral customer identity model. Contacts carry custom fields and tags; a Telegram identity can carry a verified phone number.
- `conversations` and `messages`: inbox thread and timeline. Conversations additionally carry `escalated_at`/`escalation_reason`/`escalation_type`, set when the AI agent escalates and cleared on the next human reply (temporary types also on the AI agent's next successful LLM call).
- `workflow_definitions`: workflow name, enabled state, and draft graph JSON.
- `workflow_runs` and `workflow_run_steps`: durable execution and observability records.
- `ai_agent_configs`, `ai_agent_invocation_logs`, and `conversation_ai_drafts`: AI agent configurations (several per workspace), invocation history, and pending draft replies.

## 11. Execution Requirements

- Every workflow run writes a run record.
- Every executed node writes a step record with input/output snapshots and duration.
- Workflow execution should not block webhook request handling.
- Ask Question nodes persist WAITING state and resume after contact replies.
- Active workflow runs lock the conversation so agents, the AI agent, and API clients cannot send competing replies.
- Outbound Telegram and WhatsApp send failures roll back user-created outbound message persistence.
- Future versioning should lock runs to the workflow version active at trigger time.
- Future test-run mode must avoid sending real customer messages unless explicitly enabled.

## 12. Security Requirements

- Implemented: encrypt channel credentials such as Telegram bot tokens and WhatsApp Cloud API credentials.
- Implemented: session-based auth for protected API routes.
- Implemented: email/password auth, Google OAuth, TOTP 2FA, profile management, and session invalidation.
- Implemented: password reset only via a single-use, time-boxed token (`password_reset_tokens`, 1-hour expiry) — no self-service in-place password change, removing the "confirm current password" attack surface entirely.
- Implemented: workspace-level authorization and granular permission checks for mutating workspace-scoped endpoints.
- Implemented: instance bootstrap is a one-time action guarded by an empty user table; every subsequent account requires a valid, non-expired workspace invite token — there is no open public signup surface.
- Implemented: workspace secrets encrypted at rest and never returned by the API.
- Implemented: optional contact whitelist; Telegram numbers count only when shared with Telegram's share button, never from a value typed in chat.
- Implemented: Telegram webhook secret-token verification. Planned: WhatsApp webhook signature verification beyond the initial verify-token handshake.
- Implemented: Swagger UI / OpenAPI docs are disabled unconditionally, with no env var to re-enable them — self-hosted clients only need the public API, documented separately in apps/marketing.
- Planned: mask secrets in workflow editor previews and run logs.
- Planned: audit workflow publishing, channel connection changes, permission changes, API key changes, webhook changes, and credential updates.
- Accepted gap: password reset does not proactively invalidate a user's other active sessions (see 5.3).

## 13. API And Contract Requirements

- OpenAPI must document auth (including instance bootstrap and password reset), profile/2FA, workspaces, members including ownership transfer and password-reset generation, invites, API keys, webhooks, secrets, hooks, contact access and whitelist, public API, channel accounts, contacts, external identities, conversations, messages, workflows and run logs, AI agent configuration and drafts, SSE, Telegram webhooks, WhatsApp webhooks, and normalized error responses for validation failures, missing required request parameters, business conflicts, missing resources, provider failures, and unexpected server errors.
- JSON schemas must describe normalized message events, outbound webhook events, and the persisted workflow graph format.
- Contract updates should happen in the same change set as API shape changes.

## 15. Complexity Estimate

The project is medium-to-high complexity because it combines multi-tenant auth, invite-gated account creation, MFA, profile management, permissions, invites, API keys, webhooks, channel integrations, realtime inbox behavior, workflow graph editing, durable workflow execution, external HTTP calls, an AI agent with a multi-provider LLM layer, observability, and self-hosted distribution. The current implementation has completed the first major vertical slice: Telegram and WhatsApp adapters, inbox, contacts, workflow builder and runtime, AI agent, profile/security basics, permissions, and self-hosted Docker distribution. The next complexity wall is production hardening: WhatsApp webhook signature verification, secret masking, retries, workflow versioning, and audit logs.

## 16. Positioning

RelayFlow should be positioned as a self-hosted customer messaging platform with developer-grade workflow automation and an optional AI agent. Telegram is a validation path, not the product identity. The durable thesis remains: one inbox, channel-agnostic data, and workflow automation that is inspectable, controllable, and reliable — now paired with a BYOC distribution model for teams that want to own their data and avoid recurring SaaS billing.
